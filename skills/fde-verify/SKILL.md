# 증거로 확인하고 같은 실패를 다시 검사하기

현재 과제·권한·AI 허용 단계를 따른다. 제출물 확정 이후에는 중단한다. 허용된 로컬 코드·CLI·API 검사와 참가자의 수동 화면 확인을 사용하고, Computer Use·브라우저 자동 조작·외부 자료 전송으로 대체하지 않는다.

시작할 때 아직 읽지 않은 [공통 지침](../../AGENTS.md)을 먼저 확인한다. 이번 세션에서 읽은 같은 버전이면 반복하지 않는다. 파일이 없으면 공통 규칙 미확인임을 알리고 현재 프로젝트 지침과 요청 범위 안에서 진행한다.

## 검증 범위 잡기

관련 요구와 성공 기준, DATA의 계약, 변경 파일, 기존 테스트·EVIDENCE를 읽는다. QNA에서 연결된 Q ID의 실제 답변과 현재 적용 기준을 대조하고 답변 수신을 검증 완료로 취급하지 않는다. 검토·테스트만 요청했는지 수정까지 포함되는지 구분한다. 실제 기대값을 정하는 중요한 업무 모호함은 QNA의 기존 답변을 확인한 뒤 새 질문·후속 확인으로 연결하고 독립 검사는 계속한다. 검증 중 생긴 질문을 해결 없이 테스트 기대값 변경으로 덮지 않는다.

기존 코드에 맞는 최소 검사부터 시작한다. 문법·타입·코드 리뷰는 실행 검증과 구분한다. 사용자 흐름이 없는 순수 분석 과제에 브라우저 검사를 강제하지 않는다.

## 독립 기준과 실행

- 요구에서 정상 입력·경계값·오류·빈 입력 등 중요한 실패를 고른다. 데이터 과제는 분모·단위·중복·조인 변화 중 해당 위험을 포함한다.
- 손계산·확정된 업무 사례·별도 집계처럼 구현과 독립적인 기대값을 둔다. 구현 함수가 계산한 값을 그대로 테스트 정답으로 쓰지 않는다.
- 저장·삭제·재시작 등 상태를 바꾸는 검사는 실행 전에 실제 연결 대상과 저장 위치를 확인하고, 기존 테스트 설정·임시 데이터·별도 저장소로 원본 데이터와 과제용 DB·사용자 작업 상태를 격리한다. 테스트 서버만 별도 포트로 띄우는 것은 데이터 격리가 아니다. 격리할 수 없으면 안전한 비변경 검사만 수행하고 나머지는 미실행·이유로 남긴다. 종료·정리는 이번 검사에서 만든 소유 확인된 프로세스·파일에 한정하며 사용자 미리보기 서버나 기존 DB를 임의로 중단·초기화하지 않는다. 이를 위해 새 DB·의존성을 무조건 도입하지 않는다.
- 관련 단위 검사에서 시작해 필요한 통합·입력부터 출력까지의 실행으로 넓힌다. 다른 부분의 유효한 근거를 이유 없이 전부 재실행하지 않는다.
- 명령·작업 폴더·입력·대상 버전 또는 파일 기준점·종료 코드·실행 건수·실제 출력을 기록한다. 긴 로그는 로컬 파일에 두고 필요한 결과만 요약한다.
- exit 0만으로 통과를 선언하지 않는다. 검사 0건·전부 skip·환경 오류·일부 실행은 그 범위대로 표시한다. 일부 통과를 전체 요구 충족으로 확대하지 않는다.

## 화면 기능의 검사와 직접 확인

화면이 있는 과제에서 실제 요구·구현의 핵심 흐름부터 선택한다. 정상 입력, 입력 오류, 빈 결과, 로딩·실패·재시도, 필터·선택, 저장·새로고침 중 해당 동작만 고르며 없는 기능을 만들지 않는다.

- 에이전트가 가능한 로직·API·업무 흐름 검사를 수행한다. 컴포넌트·DOM 검사는 공식 범위에서 허용되고 기존 환경에서 실행 가능할 때만 사용한다. 모의 API·DOM 검사나 HTTP 200을 실제 화면 렌더링·이벤트 연결·서버 연동의 증거로 확대하지 않는다.
- [EVIDENCE의 현업 사용 시나리오](../../templates/EVIDENCE.md#현업-사용-시나리오)를 화면 확인표로 함께 사용한다. 실제 포트·경로, 초기 조건·입력값, 조작 순서, 기대 결과와 요구/Q ID·독립 계산 근거, 자동 검사 증거와 남은 직접 확인 항목을 적는다. 과제 서버와 테스트 전용 서버를 구별한다.
- 참가자에게는 상세 표 전체 대신 같은 시나리오 ID와 **행동 → 기대 결과 → 확인 결과**만 짧게 전달한다. 행동에는 바로 실행할 수 있는 접속 위치·필요한 초기 조건·입력값을 포함하고, 확인 결과는 실제 관찰 전까지 비워 두거나 확인 대기로 둔다. 이는 기존 표의 간단한 표시이며 별도 기록을 만들지 않는다. 자동으로 재현할 수 없고 다음 작업을 막는 문제만 중간에 최소 확인을 요청하며, UI 대기와 무관한 합의된 개발·검사는 계속한다. 최종 확인을 수정·재확인할 여유 없이 제출 직전까지 미루지 않는다.
- 실제 관찰을 받기 전에는 수동 항목을 미실행·확인 대기로 둔다. 관찰은 [fde-acceptance](../fde-acceptance/SKILL.md)에서 같은 표에 연결한다. 결함 수정 뒤 영향받은 자동 검사와 화면을 다시 확인하며, 사람 확인이 필요 없는 요구에 수동 검사를 강제하지 않는다.

## 알고리즘 선택과 결과를 검증하기

중요한 방법을 선택했거나 결과의 타당성을 묻는 경우, DECISIONS의 선택 이유를 MISSION의 요구·QNA의 담당자 답변과 대조한다. 업무 기준이 맞는지, 구현이 그 기준을 지키는지, 대안보다 좋은지는 별개다. 담당자 답변 자체를 코드 검증 성공으로 사용하지 않는다.

- **독립적인 작은 정답:** 손계산·확정 사례 또는 규모가 허용하는 별도 완전탐색으로 기대 결과를 구한다. 대상 알고리즘이나 동일한 핵심 로직을 호출해 정답을 만들지 않는다. 유효한 답이 여러 개라면 불필요하게 정확한 배열 일치를 강제하지 말고 필수 제약과 합의된 목표로 평가한다.
- **필수 제약·목표값 검사:** 입력 대상의 누락·중복, 허용하지 않은 참조, 자원 한도, 시간·순서·단위 등 실제 요구에서 필요한 검사를 분리한다. 점수가 좋아도 위반 하나를 평균으로 숨기지 않는다. 정상 결과뿐 아니라 알려진 위반을 넣은 결과도 검사기에 전달해 위반을 실제로 잡는지 확인한다. 목표값은 원입력과 반환된 결정에서 독립 재계산해 보고된 값·단위와 대조한다.
- **개선 효과:** 같은 입력·데이터 버전·제약·목표 정의·실험 예산으로 기준안과 비교한다. 유효성, 목적값과 구성 지표, 실행 시간·실패를 각각 기록한다. 임의 가중치나 더 쉬운 입력으로 개선을 꾸미지 않는다. 동률 처리와 난수가 있으면 재현 조건을 기록하며, 관찰한 개선을 최적성 증명으로 바꾸지 않는다.
- **경계와 실패:** 빈 입력, 경계값, 제약 충돌, 탐색 실패·시간 초과 등 해당 위험을 검사한다. 입력 순서 변경이나 조건 완화의 기대 관계는 업무·수학적 계약이 보장할 때만 적용한다. 휴리스틱의 결과가 항상 개선된다고 가정하지 않는다.
- **변경 전파:** 데이터·조건·담당자 답변을 바꿔 영향받는 실제 계산 경로부터 최종 출력까지 확인한다. 계산 서비스는 [fde-build의 결과 계약](../fde-build/SKILL.md#계산-결과를-서비스에-연결할-때)에 맞춰 제한시간·실패 상태와 오래된 결과를 검사하고, 비동기 처리라면 응답 순서가 뒤바뀐 경우도 확인한다. 입력을 바꿔도 같은 답이 유효할 수 있으므로 무조건 결과가 달라져야 한다고 검사하지 않는다. 저장이 요구되면 실패 후 기존 상태 유지와 재조회·재시작·내보내기의 일관성을 해당 범위에서 확인한다. 화면 관찰은 참가자의 실제 확인과 구분한다.

검증 결과는 **조건 충족 범위 / 기준안 대비 품질 / 실행·재현 범위 / 최적성 또는 불가능성의 증명 여부 / 남은 위험**으로 짧게 보고한다. 실제 검사 범위 밖의 모든 입력을 보장하지 않는다. 반례가 나오면 해당 요구·결정으로 되돌려 선택을 재검토하되 검토만 요청받았다면 수정은 제안까지만 한다.

## 실패 처리

실패 입력과 기대/실제 차이 → 원인 가설 하나 → 좁은 확인 → 필요한 수정 → 원래 실패 검사 재실행 → 영향 범위 확인 순으로 진행한다. 원래 실패 기록을 보존한다.

수정은 현재 요청·권한에 포함된 범위만 수행한다. 검토·테스트만 요청받았다면 원인과 수정 제안을 보고한다. 기대값 변경이 필요하면 근거와 결정 변경을 기록하고, 통과를 위해 검사 조건을 낮추지 않는다.

같은 오류에 새 근거가 없거나 환경 제한에 막히면 반복 대신 실패 범위·허용된 대체 방법·필요한 질문을 알린다. 별도 검증 에이전트 사용은 지원 여부와 위임 허용을 따르며, 없으면 독립 기준 검증을 별도 에이전트 검토로 포장하지 않는다.

## 기록과 결과

EVIDENCE에 통과·실패·미실행·오래됨을 구분하고 R/작업 ID와 연결한다. 중요한 수정은 PLAN·DECISIONS에 연결하고 STATE의 다음 행동을 갱신한다. 원본 빈 양식은 유지한다.

사용자에게 검증한 범위, 명령과 핵심 결과, 발견한 결함, 수정·재검사 여부, 미검증을 보고한다. 코드 변경 뒤 과거 증거를 무조건 재사용하지 않으며, 검증 준비 완료와 검증 실행 완료를 구별한다.
