# 작은 완성 경로와 작업 계약 설계하기

현재 과제·프로젝트 지침과 허용된 AI 단계를 따른다. 제출물 확정 이후에는 과제 지원을 중단한다. 설계는 실제 제공 환경에서 실행 가능한 범위로 제한하며 새 도구·외부 AI·모델 전환을 전제하지 않는다.

시작할 때 아직 읽지 않은 [공통 지침](../../AGENTS.md)을 먼저 확인한다. 이번 세션에서 읽은 같은 버전이면 반복하지 않는다. 파일이 없으면 공통 규칙 미확인임을 알리고 현재 프로젝트 지침과 요청 범위 안에서 진행한다.

## 설계 입력

MISSION의 필수 요구·QNA의 관련 질문과 답변, DATA의 의미·제약, 기존 코드 구조·실행법·테스트, 실제 남은 시간을 필요한 만큼 확인한다. 기존 작업이 있으면 처음부터 재설계하지 않는다. 불명확한 성공 기준은 구현으로 덮지 않는다.

## 결정할 것

1. 대표 입력 → 핵심 처리 → 필요한 출력이 이어지는 첫 실행 경로를 정한다. 설치·UI 장식보다 중요한 계산·데이터·실행 위험을 먼저 드러낸다.
2. 과제에 필요한 가장 단순한 구성을 고른다. 분석·파일 출력 과제에 웹앱을 강제하거나, 계산 가능한 규칙을 근거 없이 LLM에 맡기지 않는다.
3. 구성별 책임과 입력·출력·오류 형식을 맞춘다. 필수 필드·타입·단위·결측·경계값·출력 순서 등 실제 결합 지점만 명시한다.
4. 각 R 요구를 구현 위치, 짧은 작업 단위, 검증 명령·기대값 근거에 연결한다. 기대 결과를 구현 출력에서 역으로 만들지 않는다.
5. 위험·의존성·가치를 기준으로 순서를 잡고 선택 기능을 구분한다. 공식 마감과 실제 시작을 기준으로 검증·설명·제출에 필요한 여유를 잡되 임의의 공식 시간표를 만들지 않는다.

선택이 업무 의미·성공 기준·필수 범위를 바꾸면 영향과 추천안을 질문한다. 이미 합의한 범위의 구현 선택이나 단계 전환마다 승인을 다시 요구하지 않는다.

## 어떤 방법이 적합한지 판단하기

방법을 고르기 어렵거나 중요한 계산·배정·탐색 방법을 결정할 때 사용한다. 단순한 규칙 구현에 불필요한 알고리즘 비교를 강제하지 않는다. 유명한 알고리즘 이름이나 AI의 자신감만으로 채택하지 않는다.

먼저 실제 입력·규모, 결정할 항목, 출력, 필수 제약, 개선 목표·우선순위, 실행 환경·시간 예산을 짧게 정리한다. 업무 기준이 비어 있으면 [fde-discover](../fde-discover/SKILL.md)의 담당자 질문으로 연결하고, 미확정 목표나 가중치를 확정 기준으로 두지 않는다.

배정·자원 선택·스케줄링·탐색 등에서 후보를 좁히기 어렵다면 [방법 선택 참고자료](references/method-selection.md)의 해당 구조만 읽는다. 단순 조회·집계에 최적화 비교를 강제하거나 전체 알고리즘 목록을 불러오지 않는다.

**옳음은 한 가지 점수가 아니다.** 다음 판단을 분리한다.

| 판단 | 선택에 필요한 근거 |
| --- | --- |
| 문제에 맞는가 | 현재 요구·데이터 의미와 방법의 전제·표현 가능한 제약이 일치하는가 |
| 결과가 유효한가 | 필수 조건을 독립적으로 검사할 수 있으며, 위반 결과를 성공으로 반환하지 않는가 |
| 더 좋은가 | 같은 입력·제약·목표에서 기준안보다 무엇이 개선되고 무엇이 나빠지는가 |
| 실행 가능한가 | 입력 규모·가용 도구·실제 시간 안에서 구현·실행·검증할 수 있는가 |

가능하면 이해하기 쉬운 기준안과 유망한 대안을 좁혀 비교한다. 각 후보의 전제, 제약 처리, 장단점, 예상 계산 비용·의존성, 실패 조건과 검증법을 DECISIONS에 간단히 남긴다. 복잡도 추정과 실제 실행 시간은 구별하며, 라이브러리 설치나 최적화 도구 사용 가능성을 확인 없이 전제하지 않는다. 대안이 실질적으로 하나라면 억지로 후보를 늘리지 않는다. 비교 전에 실제 남은 시간과 위험에 맞춰 이번 비교·실험의 종료 조건을 정한다. 후보를 계속 늘리기보다 선택을 바꿀 가장 중요한 불확실성 하나를 먼저 확인한다.

수행 범위에 구현·실험이 포함되면 작은 사례로 후보를 독립 검증하고, 비교할 기준안과 대안은 동일한 데이터·조건·시간 예산으로 확인한다. 정확한 해법을 사용할 때 별도 휴리스틱 기준안부터 만들도록 강제하지 않는다. 유효한 결과 사이에서만 품질을 비교하며, 목표 점수가 좋아도 필수 제약을 어긴 후보는 채택하지 않는다. 기준안도 유효성 검사를 통과하기 전에는 정답 기준이 아니다. 전체 UI보다 핵심 방법의 위험을 먼저 확인한다.

비교 후 사용자에게 **추천 방법 → 조건에 맞는 이유 → 대안 대비 이득·손해 → 확인된 근거와 미검증 → 선택을 바꿀 조건**을 쉬운 말과 작은 예시로 설명한다. 실험 전이라면 추천은 잠정 판단이라고 밝힌다. 핵심 알고리즘을 처음 채택하거나 크게 바꾸기 전에는 사용자의 질문·우려를 듣고 필요한 비교를 보완한 뒤 선택 방향을 확인한다. 어려운 이름만 나열해 선택 책임을 넘기거나 설명을 한 번 제공했다는 이유로 합의를 간주하지 않는다. 이해했다는 답과 채택 동의도 구별한다. 확인 전에는 그 방법의 확정 구현만 보류하고, 이미 허용된 독립 점검·작은 비교 실험은 계속한다. 합의된 방법 안의 구현·검증·작은 조정에는 매번 승인을 요구하지 않는다.

DECISIONS에 추천과 실제 선택·사용자 확인 상태, 이유·첫 독립 검증과 통과/기각 기준·비교 중단 및 복귀 조건을 남긴다. 선택 대기는 PLAN·STATE의 해당 작업에만 연결한다. 설계만 요청받았다면 첫 검증은 실행 계획이며 통과한 것으로 표시하지 않는다.

독립 검사에서 유효한 기준안이 있고 개선 시도가 실패하거나 예산을 초과하면 그 기준안을 유지할 수 있다. 기준안이 없으면 해결되지 않은 제약과 실패 범위를 알린다. `해를 찾지 못함/시간 초과`를 `해가 존재하지 않음`으로 바꾸지 않으며, 최적해라는 주장은 해당 범위의 증명이 있을 때만 한다. 작은 사례의 최적성이나 기준안 대비 개선을 전체 입력의 최적성으로 확대하지 않는다.

선택한 방법과 주장별 확인 방법을 [fde-verify](../fde-verify/SKILL.md)에 연결한다. 요구가 바뀌거나 반례·규모 문제가 발견되면 영향받는 선택과 근거를 사용자에게 설명한다. 목표·보장 수준·주요 손해나 방법 자체가 크게 바뀌면 다시 비교·합의하며, 이미 합의한 복귀 조건 안의 기준안 유지나 작은 오류 수정에는 불필요한 재승인을 요구하지 않는다. 측정된 이득 없이 전체 설계를 반복 교체하지 않는다.

## 병렬 작업을 쓰는 경우

[공통 지침](../../AGENTS.md)의 병렬 작업 규칙을 적용한다. 설계 단계에서는 PLAN에 독립 작업별 입출력 계약·수정 파일 범위·완료 확인법·통합 순서와 재실행할 핵심 검사를 구체화한다. 설계만 요청받았다면 구현 작업자를 실행하지 않는다.

## 기록과 다음 행동

PLAN 또는 기존 계획 문서에 최소 흐름·계약·작업 ID·파일 담당·의존성·상태를 기록한다. 사용자와의 방법 선택·대안은 DECISIONS, 담당자에게 확인할 업무 질문은 QNA, 현재 위치는 STATE에 연결한다. 템플릿을 채우려고 불필요한 설계를 늘리지 않는다.

설계만 요청받았다면 첫 구현 단위와 미확인 위험을 제시하고 끝낸다. 과제 수행 전체가 요청된 경우에는 명확한 첫 단위부터 이어가되, 답변이 필요한 작업만 보류한다.
