# 작은 완성 경로와 작업 계약 설계하기

현재 과제·프로젝트 지침과 허용된 AI 단계를 따른다. 제출물 확정 이후에는 과제 지원을 중단한다. 설계는 실제 제공 환경에서 실행 가능한 범위로 제한하며 새 도구·외부 AI·모델 전환을 전제하지 않는다.

## 설계 입력

MISSION의 필수 요구·질문, DATA의 의미·제약, 기존 코드 구조·실행법·테스트, 실제 남은 시간을 필요한 만큼 확인한다. 기존 작업이 있으면 처음부터 재설계하지 않는다. 불명확한 성공 기준은 구현으로 덮지 않는다.

## 결정할 것

1. 대표 입력 → 핵심 처리 → 필요한 출력이 이어지는 첫 실행 경로를 정한다. 설치·UI 장식보다 중요한 계산·데이터·실행 위험을 먼저 드러낸다.
2. 과제에 필요한 가장 단순한 구성을 고른다. 분석·파일 출력 과제에 웹앱을 강제하거나, 계산 가능한 규칙을 근거 없이 LLM에 맡기지 않는다.
3. 구성별 책임과 입력·출력·오류 형식을 맞춘다. 필수 필드·타입·단위·결측·경계값·출력 순서 등 실제 결합 지점만 명시한다.
4. 각 R 요구를 구현 위치, 짧은 작업 단위, 검증 명령·기대값 근거에 연결한다. 기대 결과를 구현 출력에서 역으로 만들지 않는다.
5. 위험·의존성·가치를 기준으로 순서를 잡고 선택 기능을 구분한다. 공식 마감과 실제 시작을 기준으로 검증·설명·제출에 필요한 여유를 잡되 임의의 공식 시간표를 만들지 않는다.

선택이 업무 의미·성공 기준·필수 범위를 바꾸면 영향과 추천안을 질문한다. 이미 합의한 범위의 구현 선택이나 단계 전환마다 승인을 다시 요구하지 않는다.

## 병렬 작업을 쓰는 경우

실제 기능 지원과 현재 지시의 위임 허용을 확인한다. 스킬을 읽었다는 사실만으로 별도 에이전트 실행 권한을 만들지 않는다. 미지원이면 같은 작업 계약으로 순차 진행한다.

독립 단위가 있을 때만 쓰기 범위를 분리한다. 메인은 공통 스키마·의존성·통합·기록 문서를 소유하고, 검증자는 별도 기대값·실패 사례를 준비할 수 있다. 같은 파일의 동시 수정이나 합의 전의 다른 API 구현을 피한다.

위임 내용에는 목적, 관련 요구·계약, 수정 허용 파일, 금지 범위, 완료 확인법, 보고할 근거를 포함한다. 통합 시점과 다시 확인할 핵심 검사를 함께 정한다.

공유 기록의 소유와 작업자 로컬 기록 위치도 구분한다. 전용 작업 폴더의 로컬 기록을 허용할 수 있지만 부모 STATE·PLAN은 메인이 갱신한다. 작업자는 변경 파일·로컬 기록 위치·실행 근거·미확정을 반환한다.

## 기록과 다음 행동

PLAN 또는 기존 계획 문서에 최소 흐름·계약·작업 ID·파일 담당·의존성·상태를 기록한다. 중요한 선택과 대안은 DECISIONS, 열린 질문은 MISSION, 현재 위치는 STATE에 연결한다. 템플릿을 채우려고 불필요한 설계를 늘리지 않는다.

설계만 요청받았다면 첫 구현 단위와 미확인 위험을 제시하고 끝낸다. 과제 수행 전체가 요청된 경우에는 명확한 첫 단위부터 이어가되, 답변이 필요한 작업만 보류한다.
