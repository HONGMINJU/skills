# 실제 업무에 쓸 수 있는지 확인하기

현재 규칙과 허용된 AI 작업 단계를 따른다. 제출물 확정 이후에는 과제 지원을 중단한다. 화면·메신저·제출은 자동 조작하지 않으며, 외부 공유나 실제 운영 시스템의 행동을 이 스킬의 권한으로 실행하지 않는다.

시작할 때 아직 읽지 않은 [공통 지침](../../AGENTS.md)을 먼저 확인한다. 이번 세션에서 읽은 같은 버전이면 반복하지 않는다. 파일이 없으면 공통 규칙 미확인임을 알리고 현재 프로젝트 지침과 요청 범위 안에서 진행한다.

## 대표 시나리오 선택

MISSION의 사용자·업무·성공 기준, QNA의 관련 답변과 실제 구현, EVIDENCE의 기술 검증 범위를 읽는다. 가장 중요한 업무 하나부터 입력 → 결과 확인 → 판단 또는 후속 행동을 연결한다. 미완료 기능은 사용 가능한 것으로 가정하지 않는다.

시나리오마다 사용자, 필요한 입력, 수행 절차, 기대하는 판단·행동, 확인할 근거를 정한다. 명시된 업무 기준이나 실제 담당자 답변을 사용하고, 모르면 추천안과 영향으로 질문한다.

## 확인할 것

- 필요한 대상·조건을 찾을 수 있는가? 출력의 단위·기간·분모·예외가 이해 가능한가?
- 결과가 나온 이유와 원자료 근거를 따라갈 수 있는가? 사용자가 해야 할 다음 판단에 필요한 정보가 있는가?
- 빈 결과·입력 오류·불확실한 결과를 정상 결과와 구분할 수 있는가? 자동 판단이 부적절한 경우 사람에게 넘길 조건이 있는가?
- 저장·재실행·다음 담당자 전달이 요구된다면 실제로 이어지는가? 요구에 없는 운영 기능을 추가하지 않는다.

현재 과제에 해당하는 항목만 선택한다. CSV·보고서·알고리즘 과제라면 그 결과물로 업무를 수행하는지 확인하고 UI를 새로 만들지 않는다.

## 관찰과 피드백

코드·CLI로 재현 가능한 부분은 허용 범위에서 확인한다. 화면 확인은 [fde-verify의 확인표 절차](../fde-verify/SKILL.md#화면-기능의-검사와-직접-확인)와 기존 EVIDENCE 행을 재사용하고 별도 기록 문서를 만들지 않는다. 사람의 이해·업무 승인은 필요한 질문과 근거를 안내하고 실제 답변을 기다린다. 확인 대기와 무관한 합의된 개발·검증·기록 정리는 계속한다.

기술 관찰, 사용자의 실제 관찰, 업무 담당자의 피드백을 구분한다. “잘 될 것 같다”는 예상이지 사용자 테스트 통과가 아니다. 담당자의 답을 받지 않았으면 수용 상태는 확인 대기로 남긴다. 개선 전후 효과는 실제 측정한 경우에만 수치로 말한다.

불일치가 생기면 결함인지 기존 요구의 모호함인지 새로운 선택 기능인지 구별한다. 결함은 관련 구현·검증으로, 업무 기준 변경은 MISSION과 설계 검토로 연결한다. 피드백을 이유로 필수 범위나 기준을 몰래 바꾸지 않는다.

## 산출물

EVIDENCE의 같은 현업 시나리오·화면 확인표에 실제 관찰·관찰자·상태와 차이·증거를 갱신한다. 자동 검사와 사용자 확인은 각각의 범위대로 남기며 별도 승인 문서를 중복 생성하지 않는다.

질문은 QNA, 실제 변경 작업은 PLAN, 중요한 수용·범위 결정은 DECISIONS, 현재 위험과 다음 행동은 STATE에 연결한다. 결과를 `실제로 가능한 업무 / 확인 근거 / 사람 확인 대기 / 필요한 수정`으로 짧게 설명한다.
