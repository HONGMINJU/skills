# FDE 작업 기록 키트

목적은 문서를 많이 만드는 것이 아니라, **무슨 문제를 풀고 있고, 무엇을 근거로 결정했으며, 다음에 무엇을 해야 하는지** 잃지 않는 것이다.

이 폴더에는 범용 지침·빈 기록 양식 8개와 **핵심 작업 스킬 7개 + 보조 스킬 2개**가 있다. 스킬은 에이전트가 읽는 작업 지침이며 완성 과제나 자동 실행 프로그램이 아니다. 공식 도구 승인·시험 환경 호환성·성적을 보장하지 않는다.

## 빠른 시작

처음에는 **시작하기 / 답변 적었어 / 지금 상태 / 마감 점검** 네 가지 요청만 기억하면 된다. 아래는 IDE의 과제 프로젝트 안에 이 저장소를 `skills`로 clone한 경우다. AI 사용이 허용된 과제 단계이며 제출물 확정 전일 때만 사용한다.

### 1. 시작하기

```text
AI 사용이 허용된 과제 단계야. 우선 문제정의까지만 해줘.
프로젝트의 skills/AGENTS.md와 skills/skills/fde-discover/SKILL.md를 읽어.
경로가 다르면 실제 키트 위치를 찾아줘.
실제 과제 안내·제공 파일에서 문제·필수 요구·성공 기준을 정리해줘.
중요한 질문은 QNA에 적고 나에게 알려줘. 답변과 무관한 확인은 계속해.
실제 과제가 없으면 도움말만 안내해. 구현·설치·외부 전송·제출은 하지 마.
```

공통 지침과 필요한 스킬만 읽으면 된다. 이 README 전체나 9개 스킬을 모두 읽을 필요는 없다. 작업 기록은 기존 지정 문서를 우선하고, 필요할 때만 키트 밖의 허용된 과제 작업공간에 만든다. 공개 빈 양식은 채우지 않는다.

### 2. 답변 적었어

> QNA의 A에 답변을 적고 저장했어. 읽고 현재 허용한 작업 범위에서 반영해줘. 반영여부에 범위와 근거를 남겨줘.

질문은 에이전트가 Q에 쓰고 알려준다. 사용자는 담당자에게 직접 물은 뒤 A에 실제 답변을 적는다. 답변을 읽는 것과 구현·검증 완료는 다르다.

### 3. 지금 상태

> 지금 어느 단계야? 끝난 것·막힌 것·내가 할 일·다음 행동만 알려줘. 조회만 하고 파일이나 테스트는 건드리지 마.

### 4. 마감 점검

> 마감 점검해줘. 확인된 남은 시간, 필수 누락·검증 근거·실행법·내가 직접 할 제출 준비를 알려줘. 우선 점검만 하고 수정·검사 실행·제출은 하지 마.

기록된 근거를 읽는 점검이다. 미실행 검사는 미검증으로 남기며 필요하면 따로 실행을 요청한다. 이미 합의된 개발 중에는 PLAN의 개선 중단 시각을 기준으로 새 실험보다 필수 누락·핵심 검증·실행 안내에 집중한다. 타이머나 자동 제출 기능은 아니다.

### 문제정의에서 개발로 이어가기

방향이 맞으면 다음처럼 요청한다. 이후에는 단계마다 다시 승인받지 않고 중요한 모호함만 질문한다.

> 합의된 범위로 필요한 데이터 확인·설계·개발·테스트를 진행해줘. 답변이 필요한 부분만 보류하고 독립 작업은 계속해. 완료·실제 검증·남은 위험을 짧게 알려줘. 자동 설치·외부 전송·Git Push·제출은 하지 마.

### 경로가 헷갈릴 때

바깥쪽 `skills`는 clone한 저장소, 안쪽 `skills`는 개별 스킬이 모인 폴더다.

```text
과제 프로젝트/
  skills/
    AGENTS.md
    README.md
    HELP.md
    skills/
      fde-discover/
        SKILL.md
```

저장소를 `fde-kit`이라는 이름으로 가져왔다면 바깥쪽 폴더명만 바꿔 `fde-kit/skills/fde-discover/SKILL.md`를 사용한다. 키트 폴더 안에서 시작했다면 프로젝트 기준 경로를 중복해서 붙이지 말고 실제 작업 위치부터 확인한다.

clone은 파일 반입이지 스킬 자동 등록이 아니다. 핵심 작업 스킬은 아직 읽지 않은 공통 지침을 먼저 확인한다. 같은 버전을 읽었다면 반복하지 않고, 공통 파일이 없으면 적용 여부를 미확인으로 알린다. 별도 설치·Codex 업데이트를 요구하지 않는다.

### 이미 clone한 키트의 안내를 갱신하려면

제공 환경에서 공개 자료 갱신을 허용하는 경우에만 사용한다. 프로젝트 폴더에서 `git -C skills status --short`로 키트의 로컬 변경 여부를 먼저 확인한다. 변경이 없고 원격이 이 공개 저장소인 경우에만 `git -C skills pull --ff-only`로 가져온다. 로컬 변경이 있거나 갱신이 거부되면 덮어쓰기·강제 reset 대신 차이를 먼저 확인한다. 공개 자료를 가져오는 작업이며 시험 자료를 Push하는 작업이 아니다.

## 메인과 서브에이전트 운영

메인은 사용자 대화·판단·통합을, 서브에이전트는 맡겨진 독립 작업을 담당한다. 위임 조건·파일 소유·질문 전달·보고·통합 규칙의 기준은 [AGENTS.md의 병렬 작업](AGENTS.md)이다.

대화 요청 예시는 [HELP](HELP.md)에서 찾는다. 이 역할 분담이 별도 상담창·즉시 응답·상시 실행을 보장하지는 않는다.

## 처음 쓰거나 현재 위치가 궁금할 때

[초보자 도움말](HELP.md)에서 바로 쓸 요청 문장을 찾는다. 두 안내 스킬은 추가 작업 단계가 아니라 어느 단계에서든 필요할 때 사용하는 보조 기능이다.

- [fde-status](skills/fde-status/SKILL.md): “지금 어느 단계야?”, “끝난 것과 남은 것 알려줘”. 실제 기록을 읽고 짧게 답하며, 조회만으로 개발·테스트·기록 변경을 시작하지 않는다.
- [fde-guide](skills/fde-guide/SKILL.md): “스킬 도우미”, “지금 뭘 쓰면 돼?”, “처음부터 쉽게 설명해줘”. 현재 상황에 맞는 기능과 요청 문장을 추천한다. 없는 스킬을 설치된 것처럼 안내하지 않는다.

현재는 스킬 파일을 작성한 상태이며 전역 설치나 시험 환경의 자동 발견을 확인하지 않았다. 파일을 명시해 읽게 하는 방식과 자동 등록은 다르다. [공식 스킬 문서](https://learn.chatgpt.com/docs/build-skills)는 형식과 호출 방식을 설명하지만, 시험에서 제공하는 버전의 호환성은 별도 확인 대상이다.

모든 스킬을 매번 순서대로 실행하지 않는다. 명확한 작은 수정은 필요한 구현·검증만 수행하고, 데이터가 없으면 데이터 점검을 강제하지 않는다. 상태·도움말만 물으면 읽기 전용으로 답한다. 스킬 9개가 에이전트 9명을 뜻하지 않는다.

처음에는 문서 상단의 빠른 시작 요청문으로 문제정의부터 확인하고, 방향이 맞으면 개발 요청으로 이어간다. 자동 발견이 확인되지 않았다면 실제 키트 안의 스킬 파일을 명시해 읽게 한다. 단순 안내·설계 요청과 실제 구현 요청의 범위를 구별한다.

## HR 등 업무 담당자 질문은 모든 단계에서

질문은 fde-discover에서 한 번 끝내는 절차가 아니다. **문제정의·데이터 탐색·설계·구현·검증 중 필요한 시점에 질문하고, 답변은 같은 기록에 모아 재사용한다.** 운영 규칙은 [공통 지침](AGENTS.md)에 있고 질문 입력 양식은 [QNA 빈 양식](templates/QNA.md)에 있다. 실제 답변은 공개 키트 밖의 과제 작업공간에 기록한다.

| 발생한 상황 | 기존 답변 활용과 후속 행동 |
| --- | --- |
| 문제정의에서 목표가 모호함 | 질문과 답변 출처를 남기고 성공 기준으로 연결 |
| 데이터 탐색에서 의미가 맞지 않음 | 관련 Q ID·적용 범위를 확인하고 새 관찰을 후속 질문으로 연결 |
| 구현 중 예외·충돌이 나타남 | 기존 업무 기준으로 판단 가능한지 확인하고 모호한 동작만 보류 |
| 검증에서 기대 결과가 불명확함 | 담당자 답변을 대조하고 필요한 기준을 확인한 뒤 독립 검증 |

새 질문을 만들기 전에 기존 답변부터 확인한다. **답변을 받았다는 것과 코드에 반영·검증했다는 것은 다르다.** 반영여부에 답변 대기·미반영·검증 대기·근거가 있는 완료를 구분하고, 답변이 바뀌면 관련 코드·결과·증거의 영향을 확인한다. 메인이 공유 대장을 통합하고 작업자에게 관련 답변과 변경을 전달한다. 메신저를 자동으로 수집하는 기능은 아니며 참가자가 실제 질문·답변을 전달해야 한다.

### 파일에서 답변하기

실제 과제에서 질문이 생기면 QNA.md에 다음 형태로 기록한다. 고유한 Q ID 아래에는 세 칸만 사용한다.

```text
## Q001
Q:
A:
반영여부:
```

1. **메인 에이전트:** Q를 작성하고 A는 비워 둔다. 반영여부는 `답변 대기`로 두고, 파일 경로·Q ID와 함께 사용자에게 HR 등 담당자에게 물어봐 달라고 알린다.
2. **사용자:** 직접 질문한 뒤 A에 실제 답변을 적고 저장한다. 정정 답변은 이전 내용을 지우지 말고 덧붙인다. 메인에게 **“답변 적었어”**라고 알리면 된다.
3. **메인 에이전트:** 파일을 다시 읽고 현재 허용된 작업 범위 안에서 요구·설계·구현·검증에 연결한다. 반영여부는 실제 진행에 맞춰 갱신하며, 완료라면 반영한 범위와 근거 위치를 적는다.

답변을 읽기만 했다면 `답변 확인·미반영`, 코드만 바꿨다면 `반영됨·검증 대기`처럼 구분한다. 설계만 요청한 작업의 완료는 설계 반영까지이며 코드·테스트 완료로 확대하지 않는다. 담당자 답변을 기다리는 동안 무관한 작업은 계속한다.

파일 감시 프로그램이나 메신저 자동 전송 기능은 아니다. 저장 알림 또는 작업 전환점에 확인하며 사용자의 A를 임의로 채우거나 덮어쓰지 않는다. QNA의 에이전트 작성은 메인이 맡고 작업자는 질문 후보만 전달한다. 기존 Q&A 문서나 실제 MISSION 대장이 있으면 보존하고 정본 위치를 STATE에 남긴다.

> QNA에 답변 적었어. 관련 Q ID를 확인하고 현재 허용한 작업 범위에서 반영해줘. 답변 수신과 반영·검증 완료는 구분해서 알려줘.

## 방법 선택이 어렵거나 결과가 맞는지 모를 때

**담당자 질문·답변 → 요구·성공 기준 → 해법 비교·선택 → 구현·독립 검증 → 설명**을 기존 스킬과 기록으로 연결한다. 스킬은 기존 9개를 유지하고, 질문 입력은 별도 QNA로 간단하게 관리한다.

- fde-discover는 실제 관찰을 근거로 필수 조건·개선 목표·업무 의미를 질문하고, 받은 답변을 요구와 작은 사례의 기대 결과로 바꾼다. 참가자가 담당자에게 직접 전달하며 답변을 추정하지 않는다.
- fde-design은 조건 충족, 기준안 대비 품질, 실행 가능성을 나눠 후보를 좁힌다. 배정·스케줄링·탐색 후보가 막히면 [방법 선택 참고자료](skills/fde-design/references/method-selection.md)의 해당 구조만 읽는다. 핵심 알고리즘은 추천 이유·대안·검증 근거를 함께 비교하고 질문을 주고받은 뒤, 사용자의 선택 방향을 확인하고 확정 구현한다.
- fde-build는 계산 결과를 실제 서비스에 연결할 때 [결과·상태 계약](skills/fde-build/SKILL.md#계산-결과를-서비스에-연결할-때)을 적용한다. 개발 중 원리 설명은 [공통 지침](AGENTS.md#개발-중-짧은-원리-설명) 한곳의 형식을 따른다.
- fde-verify는 독립적인 작은 정답·필수 제약 검사·동일 조건 비교·변경 시나리오로 확인한다. 유효한 결과, 기준안보다 나은 결과, 최적 결과를 구분한다. 검사 범위 밖의 정확성을 보장하지 않는다.

QNA의 질문·답변, MISSION의 요구, DECISIONS의 선택, PLAN의 구현 작업, EVIDENCE의 검증 근거를 ID로 연결한다. 담당자 답변이 바뀌면 영향받는 결정과 검증을 갱신한다. 기존 지정 문서가 있으면 우선 사용하고 빈 양식의 모든 항목을 억지로 채우지 않는다. 설명·협업 기록에는 실제 선택과 검증만 사용한다.

AI 사용이 허용된 과제 단계에서 이렇게 요청할 수 있다.

> 현재 요구와 데이터를 기준으로 어떤 해법이 적합한지 판단해줘. 필수 조건과 개선 목표를 나누고, 부족한 업무 기준은 담당자에게 전달할 질문으로 정리해줘. 단순 기준안과 유망한 대안을 비교해서 추천 이유·손해·한계와 독립 검증 계획을 설명해줘. 이번에는 방법 선택과 검증 계획까지만 하고 구현·실험은 시작하지 마.

개발·검증까지 원하면 합의한 범위의 구현·실행을 별도로 요청한다. 이미 전체 수행을 요청한 상황에서는 단계마다 다시 승인받지 않는다. 핵심 알고리즘의 최초 채택·중대한 변경은 함께 결정하되, 합의된 방법 안의 구현·검증·작은 조정과 답변에 무관한 독립 작업은 계속한다. 새 알고리즘 설치기나 특정 과제의 완성 해법을 제공하는 기능이 아니다.

화면이 있다면 fde-verify가 [기존 EVIDENCE 표](templates/EVIDENCE.md#현업-사용-시나리오)에 입력·조작·기대 결과와 자동 검사·남은 직접 확인을 정리한다. 참가자는 제공 브라우저에서 남은 항목을 확인하고 fde-acceptance는 실제 관찰을 같은 표에 연결한다. 브라우저 자동 조작이나 새 테스트 도구 설치가 필수인 방식은 아니다.

## 기존 스킬 안의 선택 기능

- **설명 연습:** fde-handoff에서 사용자가 직접 설명하는 연습을 요청하면 실제 근거로 질문 하나 → 사용자 답변 → 피드백 → 재설명을 진행한다. 일반 설명 요청에는 퀴즈를 강제하지 않는다. 필요한 연습 상태만 작업 사본의 HANDOFF에 남기며, 제출물 확정 후 대기·평가 단계에서는 사용하지 않는다.

## 단계별 산출물

| 단계 | 필요한 산출물 | 기록의 기준 파일 | 다음 작업으로 넘어갈 근거 |
| --- | --- | --- | --- |
| 문제정의 | 사용자·업무·문제 한 문단, 필수 요구와 성공 기준, 질문·가정 | `MISSION.md`, 질문이 있으면 `QNA.md` | 구현을 바꾸는 핵심 모호함이 해소되거나 영향이 명시됨 |
| 데이터 확인 | 행의 의미·키·단위·품질·조인 규칙, 표본 대조 결과 | `DATA.md` | 대표 입력을 해석할 수 있고 중요한 데이터 위험이 드러남 |
| 개발 설계 | 최소 실행 흐름, 구성·입출력 계약, 작업 순서·파일 담당, 검증 계획 | `PLAN.md` | 첫 구현 단위와 기대 결과가 명확함 |
| 개발 | 실제 코드·설정·결과물, 변경 요약과 구현 위치 | 실제 파일 + `PLAN.md` | 대표 입력부터 출력까지 동작함. 문서만으로 완료 처리하지 않음 |
| 테스트 | 테스트 코드·실행 로그·검산 결과, 실패·수정·재검사 기록 | 실제 테스트/로그 + `EVIDENCE.md` | 필요한 기준을 실제 관찰로 확인하고 미검증을 구분함 |
| 현업 시나리오 확인 | 사용 절차, 기대하는 업무 판단, 실제 관찰·피드백·남은 차이 | `EVIDENCE.md` | 기술적 성공과 업무상 유용성을 구분해 확인함 |
| 설명·인계 | 입력→처리→출력 설명, 선택 이유, 실행법, 한계, 제출 점검 | `HANDOFF.md` | 다른 사람이 실행·이해할 수 있고 필수 산출물을 확인함 |

테스트 기준은 설계 때 정하고, 테스트와 설명은 개발 중에도 수행한다. 데이터 발견이나 담당자 답변으로 기준이 바뀌면 필요한 단계만 다시 살핀다.

## 기록 파일은 8개

- [STATE.md](templates/STATE.md): 새 세션의 입구. 현재 단계, 가장 큰 위험, 다음 행동, 읽을 파일만 요약한다.
- [MISSION.md](templates/MISSION.md): 문제·요구·가정과 답변의 업무 해석을 Q ID로 연결한다.
- [QNA.md](templates/QNA.md): Q는 에이전트, A는 사용자, 반영여부는 에이전트가 작성하는 질문·답변의 기준 기록이다.
- [DATA.md](templates/DATA.md): 데이터 의미와 점검 결과를 보관한다. 원본 데이터 전체를 복제하지 않는다.
- [PLAN.md](templates/PLAN.md): 설계·입출력 계약·작업 상태·파일 담당을 보관한다.
- [EVIDENCE.md](templates/EVIDENCE.md): 검증 실행과 현업 시나리오 관찰의 근거를 보관한다.
- [DECISIONS.md](templates/DECISIONS.md): 중요한 선택과 이유, 기각한 대안, 변경 이력을 보관한다.
- [HANDOFF.md](templates/HANDOFF.md): 제출 확정 전에 필요한 실행·설명·인계 내용을 정리한다.

새 질문과 실제 답변은 QNA, 새 결정은 DECISIONS, 실행 결과는 EVIDENCE에 쓴다. STATE에는 요약과 링크만 둔다. 코드를 수정했다고 테스트 성공을 추정하거나 HANDOFF에 별도 성능 수치를 만들지 않는다.

## 적용 방법과 공개 범위

공개 원본은 [HONGMINJU/skills](https://github.com/HONGMINJU/skills)다. 현재 공식 안내와 제공 환경에서 공개 저장소 반입을 허용하는 경우, 기존 파일과 겹치지 않는 위치에서 다음처럼 가져올 수 있다. 이 명령은 파일을 내려받을 뿐 스킬 설치·자동 등록을 수행하지 않는다.

```sh
git clone https://github.com/HONGMINJU/skills.git
```

가져온 뒤에는 다음처럼 요청한다. 폴더 이름이나 위치가 다르면 실제 경로로 바꾼다.

> 프로젝트 안의 skills/AGENTS.md와 현재 요청에 필요한 스킬만 읽고 적용해줘. README는 필요한 안내 항목만 확인해줘. 중요한 모호함만 질문하고, 답변과 무관한 독립 작업은 계속해줘. 설치·외부 전송·제출은 하지 마.

1. 개인 준비 기록과 실제 과제 기록은 공개 원본과 분리해 보관한다. `templates/`는 빈 상태로 유지한다.
2. 시험 환경에서는 공식 안내에서 허용한 경로로 공개 자료를 가져온다. 개인 PC 파일 업로드를 전제로 하지 않는다.
3. 과제에 기존 문서나 지정 양식이 있으면 그것을 우선하고 같은 내용을 중복 생성하지 않는다.
4. 별도 기록이 필요하면 실제 과제 작업공간 안에 양식의 작업 사본을 만든다. 위치는 제공 환경과 제출 규칙을 확인해 정한다. `docs/fde/`는 위치 예시일 뿐 공식 경로가 아니다.
5. DATA는 데이터가 있을 때, HANDOFF는 필요한 내용이 생겼을 때 작성한다. 빈 문서를 채우려고 사실이나 테스트를 만들지 않는다.
6. 이 폴더를 하위 디렉터리에 clone했다고 상위 과제에 지침이 자동 적용되지는 않는다. 제공 환경에서 허용하면 `AGENTS.md`를 명시적으로 읽게 하거나 기존 지침과 충돌 없이 반영한다. 인증·전역 설정·Codex 버전을 바꾸지 않는다.
7. 공개 후보는 범용 지침과 **빈 양식**뿐이다. 작성한 과제 기록·문제·데이터·코드·결과·개인 안내문을 이 공개 원본에 넣거나 Push하지 않는다.

이 키트는 자동 설치·자동 저장·플랫폼 제출을 수행하지 않는다. 에이전트가 작업 중 파일을 갱신하는 방식이다.

대회에서 이 공개 자료를 활용한다면 결과 통지 전까지 저장소의 공개 상태를 유지한다. 공개돼 있다는 사실이 모든 기능의 공식 허가나 제공 버전과의 호환성을 뜻하지 않는다.

## 세션을 복원하는 순서

1. 현재 AI 사용이 허용된 단계인지 확인한다. 제출물 확정 이후라면 과제 지원을 재개하지 않는다.
2. 적용되는 프로젝트 지침과 작업 사본의 STATE를 읽는다.
3. MISSION의 목표·필수 요구와 QNA의 관련 답변·미반영 항목을 확인하고, PLAN의 현재 작업과 연결된 자료만 읽는다.
4. 필요한 DATA·DECISIONS·EVIDENCE의 관련 항목을 읽는다. 모든 로그를 다시 읽지 않는다.
5. 실제 코드·변경 상태와 기록이 일치하는지 확인한다. 기록이 오래됐으면 불일치를 먼저 밝힌다.
6. 확정된 다음 작업을 진행한다. 중요한 모호함만 사용자에게 묻고 독립 작업은 계속한다.

복원 요청 예시:

> AI 사용이 허용된 과제 단계인지 먼저 확인해. 적용 지침과 STATE.md를 읽고, 필요한 기록과 실제 파일을 대조한 뒤 이어가 줘. 중요한 모호함만 물어보고, 답을 기다리는 동안 가능한 독립 작업은 계속해. 확인하지 않은 테스트를 통과로 표시하지 마.

## 기록을 갱신하는 시점

- 사용자 또는 담당자의 답으로 요구나 가정이 바뀌었을 때.
- 중요한 설계 선택, 핵심 기능 완성, 중요한 테스트 실패·수정이 생겼을 때.
- 세션 전환·중단 전, 또는 제출 준비를 시작할 때.

매 도구 호출마다 저장하거나 대화 전문을 복사하지 않는다. 갱신은 변경한 사실과 근거 중심으로 짧게 한다. 예기치 않은 중단에 대비해 큰 작업을 끝낼 때 STATE를 갱신한다.
